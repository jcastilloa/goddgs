## Context

The frozen Python `HttpClient` builds `primp.Client` with both
`impersonate="random"` and `impersonate_os="random"`.  In `primp 1.3.1`,
`random_impersonate()` uniformly chooses one of 23 explicit browser versions:

- Chrome 144–148;
- Edge 144–148;
- Opera 126–131;
- Safari 26, 26.3 and 18.5;
- Firefox 140, 146, 147 and 148.

The Python binding independently chooses Android, iOS, Linux, macOS or
Windows from `IMPERSONATEOS_LIST`, then calls `impersonate_os` before
`impersonate`; that second builder call resolves the random browser version.
`primp` keeps the resulting pair with that client's cookie jar and connection
pool. It is not a per-request User-Agent randomizer.

The completed Go transport currently has one practical Chrome 146 profile for
eligible direct HTTPS requests.  It already owns explicit TLS ClientHello,
HTTP/2 framing, default headers, connection reuse and cancellation.  That is
insufficient because a real profile bundles all of those values; selecting a
different User-Agent alone would create an internally inconsistent identity.

## Goals / Non-Goals

**Goals:**

- Reproduce the source's two independent random selections, their relative
  probability and their per-client lifetime.
- Represent every source profile/OS pair as an immutable, coherent profile
  bundle: headers, TLS ClientHello specification, ALPN and HTTP/2 settings,
  pseudo-header order, regular-header order and priority behaviour.
- Capture source behaviour on loopback-only TLS fixtures and use it as the
  oracle for all profile bundles.
- Preserve current cookie isolation, cancellation, connection reuse, proxy,
  PEM and verification semantics.
- Keep production selection private and provide deterministic private
  selection only for tests.

**Non-Goals:**

- Rotating an identity between requests of the same Go transport client.
- Reimplementing `primp`'s Rust runtime, using cgo, downloading profiles at
  runtime or importing an unreviewed client stack.
- Claiming byte-for-byte equality for entropy-bearing TLS values such as
  random, key shares and GREASE payloads.  Their source-compatible structural
  semantics are the contract.
- Impersonating the *proxy endpoint* itself. For an HTTPS proxy, its outer TLS
  connection remains a verified proxy-control channel; the coherent browser
  identity is the TLS/HTTP/2 connection inside CONNECT to the search origin.

## Decisions

### Select a coherent pair once per transport client

The selector SHALL first choose one of the five source operating systems in
the Python binding's declaration order (Android, iOS, Linux, macOS, Windows),
then one of the 23 browser versions in `primp`'s declaration order. Both are
independent uniform selections. It shall construct one immutable profile
bundle and retain it for the client's lifetime. This mirrors source
construction and prevents headers, TLS and H2 from drifting apart during
connection reuse.

`math/rand` state is not shared or exported.  Production selection uses a
cryptographically seeded choice; tests inject an index-only private selector.
The injection point is private because the Python library exposes no browser
profile setting.

### Capture ClientHello semantics from frozen `primp`

The source Rust `BrowserEmulator` randomizes entropy-bearing values and
extension order per handshake. Rewriting those Rust tables by hand is both
riskier and less auditable than recording source observations. The reference
capture tool runs a loopback TLS listener, invokes an explicit `primp`
profile/OS pair, and records the public ClientHello bytes plus stable HTTP/2
fields. Those bytes contain no private key, cookie, credential or page data;
uTLS regenerates handshake entropy at use time.

Generated profile data SHALL contain the source identity, source baseline,
public ClientHello template, stable HTTP/2 fields and a checksum/provenance
record. It must be regenerated only from the frozen local Python environment.
It contains no cookies, external traffic or credentials.

### Use uTLS custom ClientHello specifications and explicit HTTP/2 bundles

The existing reviewed `github.com/sardanioss/utls` dependency remains the
pure-Go TLS layer.  A captured source ClientHello is converted to a fresh
`utls.ClientHelloSpec` at connection creation.  Dynamic random/key-share/
GREASE values are generated by uTLS for each handshake; fixed suite, group,
signature, ALPN and extension semantics come from captured source data.

The existing manual HTTP/2 transport will receive the bundle's exact SETTINGS
order, window increments, pseudo-header order, regular header order, priority
data and initial stream ID.  Header values are selected from the same bundle.
This avoids a generic H2 implementation changing a profile's observable wire
shape.

### Preserve source probability even when output shapes coincide

Some source OS choices produce identical visible header/H2 values for a
browser family.  They remain distinct selector outcomes because the frozen
source samples them independently.  The implementation can share immutable
profile data internally, but must not rebalance or collapse their probability.

### Carry the selected bundle through every HTTPS target route

The source creates `primp.Client(proxy=..., impersonate="random",
impersonate_os="random", verify=...)` as one client. Therefore a Go client
selects one bundle even when proxy, custom PEM roots or disabled verification
are configured. For direct TLS, the bundle is applied directly. For HTTP or
HTTPS proxy URLs, the transport establishes CONNECT to the target first, then
applies the selected ClientHello and HTTP/2 bundle inside that tunnel. For
SOCKS5/SOCKS5H, it applies the same bundle after the SOCKS connection.

The outer HTTPS connection to a proxy is a proxy-control leg, not the search
origin's browser identity; it retains the normal configured certificate
policy. Plain HTTP uses the tested standard transport and does not get browser
default headers because it cannot carry a matching TLS/H2 bundle.

## Risks / Trade-offs

- [uTLS cannot instantiate a captured profile] → fail generation/validation
  for that profile and do not make it selectable; extend the custom-spec
  adapter only with an executable source fixture.
- [Loopback capture differs from an external hostname] → capture SNI as a
  semantic placeholder and test that the Go profile uses the request host,
  while all other extension semantics remain fixed.
- [Per-handshake source extension-order entropy] → compare sets/order rules
  and GREASE placement classes rather than raw bytes; preserve fresh entropy
  in the Go handshake.
- [Large generated data obscures review] → store only the public ClientHello
  template and stable compatibility data, checksum it, document the generator
  and test every bundle.
- [Tunnel cancellation or failed initial dial poisons profile cache] →
  retain existing origin-cache ownership tests and add selected-profile
  variants under `-race`.

## Migration Plan

1. Add frozen profile/OS fixtures and a generated-data provenance document.
2. Add private deterministic selector and profile-bundle construction tests
   (RED).
3. Implement bundle selection, TLS and HTTP/2 adapters (GREEN), then preserve
   current direct-HTTPS behaviour behind source-shaped selection.
4. Run all offline/race/CGO-free acceptance gates and the diagnostic endpoint
   only; do not use search-engine traffic as a release gate.
5. Roll back by reverting this change: the previous fixed Chrome 146 direct
   profile remains an independently tested fallback implementation, but lacks
   the frozen source's full profile-selection behaviour.

## Open Questions

- None.  Any source profile that cannot pass the captured TLS/H2 construction
  and wire tests blocks completion rather than being silently substituted by
  a different browser family.
